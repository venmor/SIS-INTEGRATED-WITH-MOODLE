# ADR-006 — Derived registration custody for our Moodle demonstration

18 October 2026. Status: implementation decision within our explicitly authorised synthetic demonstration. Policy: **DEMO-MOODLE-REGISTRATION-2026.1**. This does not approve an institutional or production integration policy.

We need to demonstrate that a student completes formal registration and subsequently receives the corresponding Moodle course access. Our original live-test manifest required each CourseRegistration ID before sealing. That ID does not exist until formal registration commits. Keeping that condition would prevent every new registration from ever reaching Moodle in the same sealed run.

We therefore seal the exact generated Student, ProgrammeAttempt and ProgrammeOffering parents. With `DEMO_MODE=true` and `SIS_ENABLE_MOODLE_REGISTRATION_DELIVERY=true`, we derive delivery custody for a later course-registration row only when it belongs to all three exact parents, the institutional registration is REGISTERED, the student/person are active, and the course belongs to the attempt's PUBLISHED curriculum. The existing exact-manifest permit remains unchanged. Another student, attempt or programme offering never inherits permission. A saved course plan never qualifies. The staff binding source list discovers these new official rows under the sealed attempts.

Our worker additionally requires an independently activated numeric per-course/per-period shell binding, an actual target validation, a passing technical check and independent academic attestation of that same published curriculum. We use `SHELL / COURSE_PERIOD / courseId:periodId`; the older programme-wide simulator shell cannot qualify. We import an existing Moodle course through a verified binding or explicitly create its deterministic shell from the SIS binding action. Creation does not silently activate a binding.

Each source event and official course row has one durable external claim. We commit its run, source checksum, exact mapping version, lease and attempt before HTTP. We check current custody again before enrolment and finalise only the owning unexpired lease. Unknown outcomes retry by exact identity; classified refusals wait for review. Course removal suspends the Moodle enrolment and verifies absence from active participants; it never deletes submissions or grades. A multi-course registration event completes only after every relevant course row is confirmed. The source checksum includes that course's latest registration amendment, institutional status, curriculum and exact binding; an unrelated course amendment does not invalidate previously confirmed access for the unchanged course.

We normally let Moodle generate and email an initial password to a verified contact. Generated demonstration contacts cannot receive email. Our separate optional `SIS_ENABLE_MOODLE_DEMO_BOOTSTRAP=true` uses an ignored server-only `MOODLE_DEMO_INITIAL_PASSWORD` with at least 12 characters, only after the same synthetic RUNNING permit. It sets a manual Moodle account and `auth_forcepasswordchange=1`. We do not copy SIS passwords, store the temporary password in claims/audit, or return it from an API. The presenter distributes this private temporary login directly and the learner changes it in Moodle. Without the explicit bootstrap opt-in or a verified usable contact, creation waits. An existing generated Moodle account can instead be explicitly bound by its verified numeric identity and idnumber.

We checked the Moodle 5.2 API definition for `createpassword`, `password` and `preferences` in the [official user external-service source](https://raw.githubusercontent.com/moodle/moodle/MOODLE_502_STABLE/public/user/externallib.php). We checked manual enrolment against the [official enrolment source](https://raw.githubusercontent.com/moodle/moodle/MOODLE_502_STABLE/public/enrol/externallib.php).

We keep official marks separate. A confirmed current positive enrolment claim can identify the automatically provisioned Moodle user for a course's grade import. A removal, stale source, superseded mapping, foreign run or unconfirmed claim cannot provide that fallback. Moodle raw marks still enter the existing staged batch, validation, academic review and publication workflow.

Our PostgreSQL claim tests use the isolated `sis_moodle_delivery_review_20261018` database and substituted Moodle HTTP responses. They prove competing-worker convergence, bootstrap creation, read-after-write, unknown-outcome recovery, suspension and gate refusal. They do not prove MoodleCloud delivery or real browser acceptance. Those remain separate evidence to record during the connected rehearsal.

## Provider rehearsal and corrections

We verified the actual MoodleCloud course 9 and gradebook item 14 with Chanda's raw assignment mark 17/20. Moodle 5.2 returns `scaleid: null` for this numeric points item. We accept only null or zero as “no scale”, while retaining exact numeric bounds, assignment/quiz type and recalculation checks; formatted percentages never supply marks.

The public `core_enrol_get_course_enrolment_methods` response is not a complete list of active enrolment instances: Moodle's manual enrolment plugin does not implement the projection used by that endpoint. We therefore do not interpret an empty response as disabled manual enrolment. The actual manual-enrolment write validates its instance; a subsequent enrolled-user and role read confirms delivery.

We completed the real-provider rehearsal through normal SIS password sign-in, registered access, raw import, validation, independent moderation, board decision, configured demonstration release policy, password proof and an own-student result of 85%. The generated operator decisions are automated demonstration evidence, not human or institutional acceptance. Evidence lives in the ignored `.evidence/moodle-completion-20261018/` directory; credentials and tokens are excluded from Git.

Our rehearsal also exposed a fixed global three-component assumption during package assembly. We now use the exact single APPROVED course/period plan's component maxima and weights, require a complete 100% scheme, require moderated evidence from that same plan, and freeze its ID/version in the package trace. An approved one-component 20-point scheme weighted 100% therefore yields 85 from 17/20; it does not invent quiz or examination marks. The configured pass threshold and calculation formula remain separately versioned demonstration policy.

Our live worker honours the integration pause control before delegation, claim and each mutation boundary. A persisted keyset cursor advances past blocked old events, then cycles back without marking them delivered. Scoped Integration support recovery records the previous attempt proof, revalidates current source custody and queues a retry. The retry reads actual Moodle state first, preventing duplicate enrolment after a lost response. The recovery workspace displays current-run claims, reasons and the audited retry action. The additional scheduling migration requires a freshly bound live run after deployment; we never silently reuse a run sealed against a different schema fingerprint.

## Later approved presentation-only credential aid

On 18 October Charles explicitly selected a demo-only “Copy initial Moodle password” action using our generated credentials, then asked for learning access on My studies. This supersedes the earlier blanket no-password-response statement solely for this narrowly configured initial demonstration credential. It does not expose the API token, a shared bootstrap password, other students' credentials or a changed Moodle password.

We keep the generated per-username credential map in a private server environment value, separate from source and the normal student read projection. Both the explicit opt-in and the existing isolated/pinned demonstration database check are required. A session/CSRF-protected POST derives ownership from the signed-in student's registration and rechecks a current confirmed Moodle identity inside the transaction. Its no-store response supplies only that student's initial credential. Audit contains the action and registration reference, never the password. The copy action writes directly to the clipboard; passwords are not rendered, placed in URLs or saved in browser storage. We label the value initial because Moodle does not provide changed passwords. The Open Moodle link carries only the username, supported by Moodle's login source. My studies shows the access card directly, with a dashboard shortcut.
