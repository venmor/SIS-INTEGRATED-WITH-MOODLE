# NOTE-V2-MOODLE-002 — Persisted synthetic Moodle run foundation

## Behavior and authority

`TASK-V2-MOODLE-002` implements the approved 25 September design's foundation boundary under the 15 October execution amendments. Active exact sources read: Moodle Administrator §§12.15–12.37, Integration Support §§12.38–12.60, Design Sections 9/10 and permission matrices 3A/3B, plus supersession/readiness registers. Preparation requires current Moodle Administrator `manage-mapping` **and** `sync-moodle`; technical approval and retirement use `sync-moodle`; Integration Support requires `replay-event`. Every account/session/appointment must still be active and exactly match the run's organizational scope.

A Moodle Administrator prepares a database-bound `PREPARED` run, adds supported existing source references and seals the manifest. Source names do not establish synthetic provenance: the explicitly authorized isolated or exact-pinned synthetic demonstration database and the human synthetic/non-production declarations do. This control plane supports Account, Student, ProgrammeOffering, ProgrammeAttempt, CourseRegistration, TutorialGroup and TeachingAssignment references. Later delivery plans must extend the manifest with their own complete mapping/event provenance before any external mutation.

Preparation checks all target configuration independently of operator run binding. It queries the connected PostgreSQL database/server/port and successful migration ledger, hashes that evidence, and returns `requiredBinding.runId` and `requiredBinding.dbFingerprint`. An operator sets those two nonsecret environment bindings through the existing environment procedure before start/resume. Nothing edits an environment file, token or Moodle target automatically. Start/resume recompute the actual database/migration fingerprint and require the ordinary backend selection and complete configuration fingerprint to match the immutable prepared record.

The technical actor submits their own current SIS password through the dedicated reauthentication endpoint, receives a short-lived proof once, and consumes it to approve. A distinct human/person/account supplies their own proof to start; the original technical session, assignment, account, scope and freshness are checked again. The original approver cannot borrow another session or leave the approving workspace. An unchanged-target resume requires fresh operational proof and live original technical authority; expiration of the already-consumed technical proof alone does not invent a new technical approval requirement. BREAK_GLASS assignments are refused. `SECURITY-v1` supplies the synthetic proof lifetime and the per-account/action step-up attempt budget. This is an in-memory single-instance rate gate, consistent with the existing demonstration rate limiter. These synthetic password proofs do not establish approved institutional MFA.

The proof model is integration-local because this worktree has no generic exact-action password receipt service. It does not reuse historical login/MFA timestamps or alter shared identity-access behavior. The database holds hashes of proof tokens, never the raw proof/password. Proofs bind account, person, exact session, exact assignment, run, action, version and evidence checksum. Their evidence is immutable; their sole permitted update consumes them once.

The read-only identity request runs outside every database transaction. A subsequent advisory-locked transaction independently rechecks state/version, the proof, both actors and the complete binding before writing the decision. A concurrent authority/configuration/state change therefore prevents the transition. The exact release comparison and returned numeric build evidence remain separate.

Integration Support can pause, freshly resume, or fail/abandon a prepared/running/paused run. Failure releases the database's one-active-run constraint without discarding history. Failed/completed runs can close after separate technical credential-retirement and operational frozen-evidence/human-review declarations, with current independent proof. Those declarations are persisted as audit metadata; they are declarations by synthetic test actors, not independently established Charles/Chitindu human signoff. Closed runs admit no new command. The complete command always refuses `FULL_REHEARSAL_EVIDENCE_REQUIRED` in this foundation.

`RUNNING` records foundation approval only. Source delivery remains `NOT_PROVISIONED`; existing mapping, adapter mutation, claim, lease, delivery, replay and rehearsal gates remain intact. No external Moodle call was made during implementation or verification. The HTTP/SQL tests substitute only the external identity result.

## API and persistence

New routes under `/integration/live-test` expose setup, current/detail, preparation, manifest entry/seal, reauthentication and explicit lifecycle commands. Mutations require the actual session guard, CSRF marker and validated DTOs. Unknown caller-supplied approvers are rejected. Reads/commands in another scope return neutral 404; wrong-role/capability mutations return 403 and denial audit. Successful commands store exact idempotency responses; changed-key payloads and stale versions refuse. The shared contracts package exposes a dedicated `@sis/contracts/moodle-live-run` types subpath without broad barrel changes.

Additive migrations `20261016200500_moodle_live_run_foundation` and `20261016202000_moodle_numeric_version_evidence` add run, immutable transition, manifest and exact authentication-proof persistence. SQL enforces one active run per database, the closed entity/state sets, append-only decisions/entries, refusal of insert after seal, immutable seal/run binding and one-time proof consumption. No shared database was reset and no existing migration was rewritten.
