# Owned academic context discovery — 2026-10-12

[REG-001](../task-packets/TASK-V2-REG-001.md) assigns a read-only context inventory to Registration. The user-reported timetable problem arose because the generic route used configured period `2026S1` while a valid published registration existed in another period. Changing the configured period or inferring eligibility from a period name would conceal the problem.

`GET /registration/contexts` returns only eligible existing own programme attempts (`ACTIVE`/`ADMITTED`) paired with the existing configured current period or authoritative own plan/registration period rows. Inner joins exclude legacy orphan IDs. It validates the selected active STUDENT/study appointment, active account/person/student, ownership and student scope at read time; both the student ID used by fixtures and student number used by the conversion service are accepted as scope identifiers. Other roles cannot borrow student discovery.

The shared `RegistrationContextsResponse` exposes programme/intake, period code, nullable authoritative calendar facts and registration state. A submitted plan without confirmed registration is `REVIEW_REQUIRED`, never an editable draft or successful registration. Cancelled registrations are review-only. `soleRegisteredContext` considers the whole population of ACTIVE registered pairs; it does not assume the first page is complete or count admitted attempts as confirmed active registration.

Twenty-row keyset pages are ordered by period code and attempt ID using the same PostgreSQL C collation for filtering and ordering. The signed cursor binds purpose/version, account, selected appointment, student and configured-period policy. Altered, foreign, repeated, empty, oversized or unknown query filters fail closed. Production requires the existing private `QUEUE_CURSOR_SECRET` (at least 32 characters), as do other scoped queues. Cursor traversal is live discovery, not an eligibility grant or frozen official-record snapshot. Each page and whole-population sole-registration check share a repeatable-read database transaction. No schema change, registration mutation, policy-default change, grade fabrication or automatic course selection is introduced.

Calendar names/dates come only from the active setup activation's period version. Draft names do not appear. Missing facts remain null; period codes are not parsed into academic dates or semester eligibility.

Initial connected run on the preserved isolated target `sis_setup003_test_2026101203` observed fourteen missing-route failures (404) before implementation. The focused connected suite covers ownership, current options, orphan/withdrawn/completed exclusions, multiple attempts, more than twenty pairs, sole registration beyond page one, foreign/forged/appointment-bound cursors, role/identity/assignment/capability denials, expiry/future/foreign scope, cancelled status, unknown query filters, calendar draft versus activation and no plan/registration writes. Final connected suite: 21/21 passed, including calendar draft/activation behavior and cursor traversal after the explicit purpose binding. Existing registration query/status units: 16/16 passed. API no-emit typecheck passed. No shared database was reset.
