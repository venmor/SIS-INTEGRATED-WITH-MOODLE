# V2 fictional master and course timetable previews — 2026-10-05

Task: [TASK-V2-TIME-006](../task-packets/TASK-V2-TIME-006.md). Decision: [ADR-004](../adr/ADR-004-synthetic-timetable-planning-contract.md). Human acceptance pending.

The better planning boundary is one immutable master version for a fictional academic period. The course timetable is filtered on the server from that exact version, so a course view cannot drift through a separate edit. A central fictional timetable coordinator can select real draft delivery identities, an appointed teacher, room, dated session, saved complete rule and explicit enrolled-course links. Server resolution supplies campus, capacity and participants. The browser cannot assert trusted roster or appointment facts. The full conflict pass reports room/teacher/student overlap, access, travel, teaching-window, seat-plan and missing-coverage findings. An empty or incomplete official course-registration mapping is blocked, not silently filled with invented student memberships. Whole-master findings also appear in a course projection.

This revises the ADR's initial suggestion that campus draft versions contribute to the master: for this slice, separately editable campus timetables would create version and merge ambiguity without publication policy. Campus staff retain scoped rule authorship; the fictional central coordinator owns the single preview draft. Delegated section editing, if later needed, requires a versioned proposal/merge contract and appointment checks. This is a reasoned implementation refinement, not institutional policy approval.

The isolated review seed contains two synthetic course sections, a room and teaching assignments, but no invented official student registration. As a result, the demonstration master correctly shows `BLOCKED` until an authorized registration/section-mapping flow supplies real links. The saved row and audit event are append-only; retries use a client reference, stale versions return 409, and revoked or student sessions cannot read drafts. The public/student timetable remains untouched.

## Access and discovery correction

The user could not find the preview from Nasilele's campus account. The seed deliberately assigns `nasilele.scheduler` only `DOMAIN_ADMIN/CAMPUS:DEMO-MAIN`; `nasilele.master` holds the separate `TIMETABLE_COORDINATOR/SYSTEM:DEMO-UNIVERSITY` appointment. Workspace switching is confined to appointments on the same account. The discovery defect was that neither timetable account appeared in demo sign-in, the isolated web server did not enable its demo cards, and the saved preview followed the long editor. Demo sign-in now names both accounts and their different purposes under the two explicit demo switches, directs successful timetable logins to their permitted workspace, and places the saved master/course preview before the editor. The own-session policy allowlist also omitted both timetable roles; it now allows their own-session read/switch verbs. Target ownership, liveness, separation-of-duties and timetable-specific access checks still apply, and these roles gain no IAM grant or publication verb. Regression tests cover both roles, active-role changes, foreign and revoked appointment denial. The local preview runs at port 3154, separately from the older 3100 instance.

## Larger preview rehearsal

The user requested more courses for an overall view. The isolated seed now adds ten clearly fictional `DEM101`–`DEM110` courses alongside SWE111/MTH111, delivery sections and four rooms. The new courses have no curriculum links or official registrations. `scripts/timetable-demo-sample.mjs` saves 24 dated sessions across 5–9 October 2026 through the actual coordinator API using the saved rule version. Stable content-derived references make unchanged retries idempotent. The server snapshots each course-version title. The UI orders sessions by date/time, summarizes courses/rooms/days, filters by day, pages ten rows, and groups repeated findings in keyboard-accessible disclosures. Course requests ignore superseded responses and show a loading state instead of claiming no findings while a response is pending. This remains a bounded rehearsal; server paging/search for larger datasets is still required.
