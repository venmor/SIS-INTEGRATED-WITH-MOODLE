# Aim, Objectives, Scope and Boundaries

## Aim

Design and later implement a secure, usable and traceable SIS–Moodle platform that supports the student lifecycle while preserving institutional authority and enabling two developers to learn and explain the system.

## Objectives

1. Define authoritative domains, records and state transitions.
2. Provide role- and scope-specific user experiences.
3. Integrate Moodle and other providers through governed contracts and reconciliation.
4. Protect privacy, restricted records, financial integrity and official results.
5. Create accessible, responsive and plain-language interfaces.
6. Make policy and institutional variation versioned configuration.
7. Establish Git, CI/CD, testing, release and recovery controls.
8. Keep AI assistance consistent through repository memory, task packets and human review.
9. Build a connected presentation MVP, then expand modules through evidence-based releases.
10. Preserve learning and traceability so both developers can defend high-level and code-level decisions.

## In scope

Admissions, student records, registration/progression, academic delivery, Moodle integration, assessment/examinations, finance, postgraduate research, support services, graduation/credentials, quality/governance, reporting, notifications, audit, access administration and integration operations.

## Out of scope for the documentation ZIP

Application code, real provider credentials, production student data, live payment processing, production deployment and institution-specific policy values that have not been approved.
