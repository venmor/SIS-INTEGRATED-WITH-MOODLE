# Step 0 — Design and Policy Gate

**Release target:** Design baseline 3.0.0

## User/system outcome

The team can select the first implementation task without relying on chat memory or unapproved policy. Every role family has a controlling standalone or composite journey and source lineage.

## Read before planning

- START-HERE and authority rules
- Role catalogue and selected journey books
- Functional requirements, permissions and traceability
- Security/resilience and development entry gate

## Learning goals

- Difference between examples and approved institutional policy
- Requirement-to-test traceability
- How to create a design-gap record and ADR

## Ordered delivery slices

1. Review composite role books with the supervisor and confirm names/authority
2. Record demo-only versus institution-approved policy/configuration
3. Confirm hosting, identity, Moodle and provider decisions needed only for the MVP
4. Create the first task/backlog and rotation ledger

## Security, integrity and recovery focus

- No real student data or production credentials
- Confirm restricted-data classifications and high-impact approval roles
- Define who approves policy/configuration changes

## Required proof

- Manual coverage review for every MVP handoff
- Traceability spot-check from requirement to role/action/permission/test
- Supervisor/team sign-off on open decision register

## Team rotation and documentation

Charles and Chitindu jointly perform this gate. Each independently explains the applicant-to-student and Moodle-authority boundaries before dividing tasks.

## Demonstration checkpoint

Walk through the handbook, one role journey and the planned release map without showing code.

## Exit gate

- No MVP task has an unresolved authority or visibility question
- Demo-only values are labelled
- Backlog tasks are small and ordered
- Lead/reviewer assigned for Phase 0
