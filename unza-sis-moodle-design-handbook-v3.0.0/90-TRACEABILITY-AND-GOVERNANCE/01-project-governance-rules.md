# Project Governance Rules

1. Human developers and the supervisor retain design and release authority.
2. AI assistance cannot approve policy, security exceptions or high-impact records.
3. Every task begins from an approved issue/task packet and ends with evidence.
4. One protected `main` branch represents releasable truth.
5. The other developer reviews every change; high-impact changes require explicit human sign-off.
6. Institutional variation is effective-dated configuration with owner, reason, approval and tests.
7. Official records are versioned; corrections preserve history.
8. Security/privacy/permission rules override convenience and UI visibility.
9. Demo configuration/data is fictional and never presented as UNZA policy.
10. A design gap pauses only the affected work and is resolved through a recorded decision.
11. Release names and module maturity are honest: designed, scaffolded, functional or operational.
12. Superseded records remain available for provenance but do not control new work.

## Policy/configuration governance

Each academic, finance, workflow, role, reporting, integration and retention configuration stores identifier, version, scope, effective dates, owner, approval status, reason, prior version, validation and test fixture. Hard-coding a fee, grade boundary, approval chain, provider ID or programme rule violates the design.
